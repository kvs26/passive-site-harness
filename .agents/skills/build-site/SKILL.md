# Build Site

Turns a site PRD (from `/to-spec`, following `docs/agents/site-prd-template.md`) into a running Astro
site at `sites/<slug>/`. This skill **owns the template and the build procedure**; the site owner
**owns the data and the links** — the agent never invents either, only shapes what it's handed.

Everything specific to one site — its config, its dataset, its brand assets, its `wrangler.jsonc` —
lives **only inside `sites/<slug>/`**. Nothing about a specific site is ever written back into this
skill's bundled `assets/house-template/`; that folder stays the generic starting point for the next
site. (There is no more `factory/house-template/` — that folder's contents now live at
`assets/house-template/` inside this skill, per the `site-factory-v1` map's "Extract the factory"
ticket.)

## Hard rules

- **Never invent data, links, or numbers.** Dataset rows, product URLs, and traffic/monetization
  figures come only from what the site owner hands over, or from a link the agent itself fetched and
  verified this session. If something's unknown, leave it unknown rather than guessing.
- **Monetization signup is always the site owner's own action.** Applying for Google AdSense, joining
  Amazon Associates, minting a tracking tag — the agent never does these and never fabricates
  credentials or ids. The agent only flips the config switches once the owner confirms the account
  exists and hands over the real publisher id / tracking tag.
- **Never mutate `assets/house-template/`** while building a specific site. Copy it, then edit only the
  copy under `sites/<slug>/`.
- **One seam for config.** All per-site identity/theme/monetization settings live in
  `src/lib/site.config.mjs` — don't scatter site-specific values into components.

## Procedure

### 1. Scaffold

1. Confirm the site's slug (matches its `sites/<slug>/` directory and, loosely, its domain).
2. Copy `.agents/skills/build-site/assets/house-template/` → `sites/<slug>/` (whole tree except
   `node_modules/`, `dist/`, `.astro/` — those get regenerated by `npm install` / `npm run build`).
3. `npm install` inside `sites/<slug>/`.

> **Reminder for later:** once the owner's raw data lands in step 5 as a master CSV
> (`record_id, platform, brand, model, product, ...`), `assets/scripts/` has two link-finder
> scripts for step 6 — see their own `README.md`. Don't forget they exist just because they're
> not needed yet.

### 2. Discuss the design choices — always, don't default silently

Before touching config, ask the site owner to choose the look and feel. **Explain each option in
plain terms every time** (don't assume they remember from a past site) and let them react before
locking anything in:

- **Skin** — the color/font ramp. Describe each: `neutral` (clean, default, safe for any niche),
  `editorial` (magazine-like, serif-leaning, guide/content niches), `technical` (dense, monospace
  accents, spec/tool niches), `dark` (dark-mode-first), `playful` (rounder, brighter, casual niches).
  Recommend one based on the PRD's niche/tone, but let them pick.
- **Layout mode** — `list` (results-list, good for spec/tool comparisons) vs `grid` (card-grid, good
  for image-led/product niches). Explain which the PRD's page map implies and why.
- **Dark-mode toggle** — on/off; explain it's a free visitor option layered on top of the chosen skin,
  not a separate skin.
- If they're unsure or want to see it first, offer to run `npm run dev` after scaffolding with a
  couple of skins/modes so they can look before committing — don't force a decision on description
  alone if they'd rather see it.

Record their choice; don't proceed to config until they've confirmed.

### 3. Custom tool logic, if the PRD calls for it

Config and dataset only cover data-driven pages. If the PRD's "Core job" describes real logic beyond
listing/filtering data — a calculation, an interactive widget, anything with its own behavior — that's
**a real implementation task, not a config-fill**. Always remind the owner of this sub-flow when the
PRD implies one, rather than silently skipping it:

1. Run **`/to-tickets`** on `prd.md` to break the tool-logic work into implementation tickets.
2. Tickets live in **`sites/<slug>/.scratch/<slug>/issues/`** — the site is its own independent repo,
   so its tracker lives inside it, not in this repo's root `.scratch/`.
3. Run **`/implement`** per ticket (or **`/tdd`** if the logic is calculation-heavy/testable).
4. Run **`/code-review`** before considering the tool done.
5. Skip `/grilling-with-docs` and `/domain-modeling` unless the tool genuinely needs external-API
   research or has real domain complexity — the PRD has usually already resolved the ambiguity. Skip
   a full `/wayfinder` map too — scope is already fixed, there's no fog left to chart.

If the PRD is pure data/listing (no bespoke logic), skip this step entirely.

### 4. Fill the config seam

Edit `sites/<slug>/src/lib/site.config.mjs` from the PRD and the design choices above: `url`
(placeholder until domain is bought), `name`, `tagline`, `skin`, `layoutMode`,
`enableDarkModeToggle`, `nav`/footer links, `organization`. Update `public/site.webmanifest`
(`name`/`short_name`) too — it's a separate file the template doesn't auto-sync, and it's easy to
forget (site #1 shipped with this still saying "House Template").

Rename `wrangler.jsonc`'s `name` field to the slug.

Leave `monetization` all `enabled: false` — that's step 6, not now.

### 5. Turn raw material into the dataset

This is the step that needs judgement, not just copying. **First check `sites/<slug>/raw-source/`
for files already dropped there** — only ask the site owner for raw material if that folder is empty
or missing. Ask for a CSV (often the easiest — one row per product, with data *and* buy-link columns
together), a markdown file, a PDF, a spreadsheet, or just pasted notes — describing the real items the
site should carry (whatever the PRD's "Data source" section says the site catalogs: products, entries,
comparisons, whatever the niche's unit is). Save whatever they hand over directly into
`sites/<slug>/raw-source/` (create this folder — flat, no subfolders — the first time it's needed; see
`sites/runs-on-your-battery-finder/raw-source/README.md` for the convention) so the original material
stays next to the site for future refreshes.

1. Read whatever they hand over. Extract the natural groupings the PRD's Page map implies (e.g. this
   niche's `platforms` and `categories`) and the individual entries (`products`) within them.
2. Shape it into `src/data/catalog.json`'s schema, following the real shape proven by site #1
   (`sites/runs-on-your-battery-finder/src/data/catalog.json` is a good live reference — adapt field
   names to the niche, the shape doesn't have to be identical):
   ```jsonc
   {
     "platforms": [{ "slug": "...", "name": "...", "brand": "..." }],   // top-level grouping(s)
     "categories": [{ "slug": "...", "name": "..." }],                  // cross-cutting grouping(s)
     "products": [{
       "id": "...",                 // unique per row
       "name": "...",               // full name incl. model/variant
       "platform": "...",           // slug into platforms
       "category": "...",           // slug into categories
       "fit": "native|direct|adapter",  // or whatever verdict labels this niche's PRD defines
       "note": "...",               // hand-verified explanation, in the owner's own words if given
       "affiliate": {
         "affiliate_url": "",       // filled in step 6
         "affiliate_enabled": false,
         "requires_disclosure": true
       }
     }]
   }
   ```
3. **Do not invent rows or verdicts.** If the raw material doesn't say whether something fits, leave
   the field `null`/unknown and flag it back to the owner rather than guessing a plausible-looking
   value. Every `fit`-style verdict must trace to something the owner actually told you.
4. Confirm the row count and a few samples back to the owner before moving on — cheap to catch a
   misread column now.

### 6. Attach product/affiliate links

Links often arrive **in the same CSV** as the dataset from step 5 (a buy-link column alongside the
product row) — if so, there's nothing new to check, just pull the link from that row. Otherwise,
**check `sites/<slug>/raw-source/`** for a separate links file dropped there — only ask the site owner
for raw links if none exist. Save whatever they hand over into `sites/<slug>/raw-source/`. Then:

1. Match each link to the dataset row it belongs to (by product name/model — ask the owner to
   disambiguate anything you can't confidently match; don't guess).
2. If links are missing rather than supplied, `assets/scripts/` (see its own `README.md`) has two
   discovery aids that search for candidate product pages from a master CSV of
   `platform/brand/model/product` rows and score them — pick based on where this site's links
   should point: `find_amazon_product_links.py` is **Amazon-only** (searches `site:amazon.com`,
   only accepts `/dp/<ASIN>` pages); `find_product_links.py` searches **any domain** (open web, or
   an optional `--domains` allowlist) for sites that link to multiple retailers/manufacturers.
   Neither is a substitute for verification; treat every candidate the same as a manually-found
   link.
3. **Verify each link resolves** (fetch it, confirm it 200s and looks like the right product/page —
   not just that the URL is well-formed) before writing it into `affiliate.affiliate_url`. Flag any
   link that fails or looks wrong rather than writing it in anyway.
4. Ask the owner: **enable `SITE.monetization.productLinks`?** (plain, untagged, undisclosed outbound
   links — safe pre-launch and pre-Associates-approval, off by default). Don't leave this unasked;
   it's a real decision, not a default to skip past. If yes, set
   `SITE.monetization.productLinks.enabled = true`.
5. Leave `affiliate.affiliate_enabled` and `SITE.monetization.affiliate.enabled` off — those flip only
   after the owner has actually joined Amazon Associates and hands over a real tagged deep link (a
   manual, later act by the owner, outside this skill's scope — see "Monetization is manual" below).

### 7. Build and hand back

`npm run build` inside `sites/<slug>/`; confirm it succeeds and the page count looks sane (roughly:
tool page + one page per platform×category + the trust/legal set). Report back what was scaffolded,
what's still `unknown`/unresolved from steps 5–6, and what the owner still needs to do (domain, Git
push, Cloudflare wiring — see the deploy checklist in `docs/agents/` if one exists, otherwise the
generic GitHub → Cloudflare Pages/Workers flow: push `sites/<slug>/` as its own repo, connect it in
Cloudflare, attach the domain).

## Monetization is manual, always

This skill never signs up for anything. AdSense approval, Amazon Associates approval, and minting
tracking ids/tags are 100% the site owner's own actions, done outside any agent session. The skill's
job stops at: reserving the ad/affiliate holes in the template (already built in), asking whether
`productLinks` should go on pre-approval, and — later, whenever the owner asks, in a follow-up
session — flipping `SITE.monetization.ads.enabled` / `SITE.monetization.affiliate.enabled` once they
hand over the real publisher id / tagged links. There is no "apply for AdSense" or "join Associates"
step in this skill; don't add one.

## Post-launch: feature notes

Every scaffolded site ships with `feature-notes/` (see its own `README.md` for the full workflow) —
where the site owner drops new feature ideas whenever they occur, any time after launch. The loop:
drop a note → run `/to-tickets` on `feature-notes/` (tickets land in `sites/<slug>/.scratch/<slug>/issues/`,
consumed notes move to `feature-notes/done/`) → `/implement`/`/tdd` the ticket → mark it
`Status: resolved`. This skill's own procedure above only covers first-build; feature notes are how a
site grows afterward without re-running `/build-site`.

## What's bundled

`assets/house-template/` is the full generic Astro scaffold (layouts, skins, SEO baseline, ad/affiliate
holes, page set) — see its own `README.md` for what's in the box and the skin/layout-mode system.

`assets/scripts/` holds standalone helper scripts used during step 6, not part of the Astro
scaffold itself — see its own `README.md`. Currently: `find_amazon_product_links.py` (Amazon-only
direct product-page search) and `find_product_links.py` (open-web/any-domain product-page search).

The template folds in lessons learned from actually shipping `sites/runs-on-your-battery-finder/`:

- `AdSlot.astro` only shows its reserved-space placeholder box in dev — a real production visitor
  never sees an empty grey "Ad slot" box before ads are turned on.
- `wrangler.jsonc` is bundled from the start (Cloudflare's dashboard onboards new static sites via
  Workers, not the classic Pages UI — deploy needs this file with `assets.directory: ./dist`).
- Copy/tone: site #1's shipped copy favors plain language over jargon in places (e.g. "fits as-is"
  over "direct-fit", "checked by hand" over "hand-verified"). The bundled template keeps its own
  generic wording — match the PRD's target audience's voice per site rather than copying site #1's
  wording verbatim.
- The Astro whitespace-before/after-`<a>` bug (a line break right against an `<a>`/`</a>` tag eats the
  adjoining space) — keep prose that touches a link on the same source line as the tag. Check every
  prose page (about/contact/disclosure/methodology/privacy/faq) if you fix one instance.

## Performance and UI lessons from `sites/board-game-expansion-buyers-guide/`

Site #2 feels faster and looks better than the bare template. When building a new site, apply these
(performance and UI only — they don't change the config seam or data rules above):

**Performance**

- **Embed the search index in the page.** Emit a small, pre-normalized index as
  `<script type="application/json" id="...">` (escape `<` as `\u003c` via
  `JSON.stringify(data).replace(/</g, '\\u003c')`) and parse it in vanilla JS. No extra fetch, no
  framework, minimal client JS. See `src/pages/index.astro` and `src/lib/game-search.mjs`.
- **Normalize text for matching** (NFKD, strip diacritics, lowercase, `&`→`and`) on both the query and
  the index so search feels forgiving.
- **Prefer inline SVG over image files** for logos, hero art, and item glyphs (colors/shapes computed
  from a small map in `src/lib/`) — zero image requests, no layout shift. See `HeroArt.astro`,
  `game-art.mjs`.
- **Font loading:** `font-display: optional` for body text, `swap` for the display font, to avoid
  layout shift. See `src/styles/tokens.css`.
- **Do interactive logic in one render pass:** a single change listener on the form updates all
  dependent visuals; persist selections in the URL query string plus `localStorage` so state is
  shareable and survives reloads.
- Compute derived data (rankings, dependency chains) at build time; ship only what the client must
  recompute.

**UI**

- **Map data enums to label + tone in one shared module** and render them through one badge component
  (`guide.mjs` `VERDICTS` + `Verdict.astro`) so verdicts look consistent everywhere.
- **Give components a `compact` mode** (e.g. `BuyLinks.astro`: first few links inline vs. full
  "where to buy" block) for list rows vs. detail pages.
- **Surface warnings/prerequisites visibly** with an inline-SVG icon block, hidden when empty.
- Keep the homepage centered on one obvious search/tool entry plus illustrated hero, with a
  cohesive token-driven type/spacing scale in `src/styles/tokens.css`.

**Search bar (homepage)**

- Render the full item list server-side (every `<li data-game-item data-slug=...>` is in the HTML, so
  it works for crawlers and no-JS), and ship the search `<form data-game-search hidden>`; JS unhides
  the form and only filters. Progressive enhancement, no layout shift.
- Filtering just toggles `li.hidden` from a `matchGame(entry, query)` helper in `src/lib/*-search.mjs`
  that also matches aliases/child items and returns `via` (why it matched), shown as a "Has: ..." hint.
- Live `input` listener (no debounce needed at this size), `submit` is `preventDefault`ed, and an
  `aria-live` status line reports "N of M match" or an empty-state that points to `/contact`
  ("Nothing matches X yet. Tell us and we'll add it").
- Always end the list with a "Don't see yours? Tell us" link to `/contact` — demand signal for the owner.

**Contact page / button**

- No form, backend, or third-party script: `/contact` is a static page with one prominent
  `<a class="btn" href="mailto:<owner email>">Email us</a>` (use the owner's real address from the PRD;
  never invent one). **Also show the address as plain visible text** next to the button (visitors
  without a configured mail app get nothing from a bare `mailto:` button and need to copy it), followed by a short "most useful things to send" list (mistake / missing item /
  disagree with a verdict) so emails arrive actionable.
- Put `Contact` in `SITE.nav` and the footer; link to it from search empty-states and the
  "not listed?" line. Keep the "Email us" link text on the same line as its tag (Astro whitespace bug).

Reference the board-game site's `src/` for concrete implementations before designing from scratch.
