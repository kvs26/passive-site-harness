# Map: passive-site-harness V1 spec

Label: wayfinder:map
Status: open

## Destination

A V1 spec for `passive-site-harness`, published to the tracker via `/to-spec`, covering pipeline stages 1–4 (idea discovery → validation → top-3 presentation → per-site PRD) — ready to hand to an implementation session.

## Notes

- **Target market: US by default** — niches, queries, Trends geo, forums, datasets, and monetization all assume US unless an effort overrides it.
- Solo side project; lean. Not a SaaS, startup, or automated website factory.
- Harness form factor: **skills + markdown files on disk**, no app/CLI. Deterministic scripts only where an operation proves fragile.
- Skills to consult per session: `/grilling`, `/domain-modeling`, `/research`, `/prototype`.
- Cost/effort is not a constraint; research should be deep. Bounds are about *shape* (checklists, quotas), not thrift.
- Hard rules: never invent search volume/CPC/difficulty/traffic/revenue figures — "unknown" is a first-class value. No paid SEO tools or APIs in V1.
- Website idea principles: prefer "do it" over "answer it" tools; reject ideas one LLM reply solves; every idea needs a specific hook. Sites are static HTML/CSS/JS, no accounts/DB/backend, mobile-friendly, crawlable, cheap to host.
- Human checkpoints (always manual): idea selection, PRD approval, final review, domain purchase, deployment, community posting, AdSense, anything spending money.

### Settled during charting

- V1 scope = stages 1–4 only. Stages 5–8 (build/test/preview/deploy) are per-site work using existing skills (`/implement`, `/tdd`, `/code-review`); harness support for them is a possible V2 extracted from real experience.
- Two project skills: `idea-scout` (bounded discovery) and `idea-validate` (evidence dossiers). PRD stage reuses `/to-spec` + a site-PRD template — no custom PRD skill.
- Discovery runs: checklist-bounded source passes per niche, manually triggered, one run per session, ending with 3–5 candidates on disk (weak ones included, with evidence).
- Validation: two-pass — hard gates in scout (fail = die in run log with reason), deep dossiers in validate. Qualitative rubric (strong/weak/unknown per signal + confidence grade), **no numeric scores**. Comparison brief when ≥3 validated; user picks; only picked ideas get a PRD.
- PRD → build flow: `/to-spec` → (optionally `/to-tickets`) → `/implement` or `/tdd`.
- First vertical slice = one full pass on a single niche: write both skills, run scout once, validate survivors, user picks one, `/to-spec` produces its PRD. That pass is the V1 acceptance test.
- Reddit stays in the source mix as a first-class but **optional** signal — never a single point of failure. Access ladder: DDG/SERP `site:reddit.com` search → normal browser access → manual research checkpoint → authenticated OAuth API later. Scout must degrade gracefully when Reddit is unreachable, leaning on US-focused forums, app reviews, autocomplete, Trends, public datasets, and competitor research.

## Decisions so far

<!-- one line per closed ticket -->

- [Free idea-research sources: what can an agent actually access?](issues/01-source-access-research.md) — autocomplete JSON endpoint + DDG SERPs + HN Algolia + iTunes review RSS are the reliable free core; Reddit needs OAuth or DDG proxying; Trends/Keyword Planner are manual-export passes. Full table in [research/01-source-access.md](research/01-source-access.md).
- [Scout checklist and hard gates](issues/02-scout-checklist-and-gates.md) — user picks 1 niche from 3–5 agent proposals; demand-first pass order (autocomplete → pain mining → SERP/competitors → Trends/datasets); full source catalog (Q&A/complaints, demand phrasing, product gaps, trends, communities) with agent picking 5–8 sources per run spanning ≥3 signal groups — none mandatory; outcome-bounded at ~25–40 problem statements; six hard gates; two fetch scripts with pluggable adapters, optional credentialed adapters via `.env` (never committed), graceful degradation when credentials absent.
- [Validation rubric and dossier structure](issues/03-validation-rubric.md) — six merged signals (demand, SERP/competitor weakness, hook depth, monetization, feasibility+maintenance, unique data); strong/weak/unknown grades each with a one-line why + real evidence (≥2 independent, fresh-ish sources for strong); high/medium/low confidence = "how much digging backs this up"; six-section dossier layout and four-part comparison brief (table, per-idea paragraphs, labelled opinion, human-pick prompt).
- [Pipeline state layout and idea lifecycle](issues/04-pipeline-state-layout.md) — `pipeline/<niche>/` grouping with `niche.md`, `runs/` (scout + validate logs), and `ideas/<slug>/{idea.md, dossier.md, prd.md}`; lifecycle candidate → validated → picked → spec'd (+ rejected/parked, no `built` in V1); canonical `Status:` line in `idea.md` with a derived global `pipeline/board.md` regenerated by state-changing skill sessions.
- [Prototype: idea-scout SKILL.md draft](issues/05-prototype-idea-scout.md) — draft accepted as the skill's settled shape: [prototypes/idea-scout-SKILL.md](prototypes/idea-scout-SKILL.md); seeds input, per-candidate gate results, scout-owned board/niche upkeep, and auto-invocable description all kept; refinement deferred to post-testing.
- [Prototype: idea-validate SKILL.md + comparison brief draft](issues/06-prototype-idea-validate.md) — drafted [idea-validate SKILL.md](prototypes/idea-validate-SKILL.md) and [comparison-brief template](prototypes/comparison-brief-template.md); one idea per run, scout evidence re-verified, early-stop on dead demand, validated/rejected/parked transitions defined, brief regenerated (not stacked) at ≥3 validated; accepted as-is pending first real use.
- [Site-PRD template for /to-spec](issues/07-site-prd-template.md) — standalone template at [docs/agents/site-prd-template.md](../../docs/agents/site-prd-template.md), attached at `/to-spec` invocation (skill unmodified); extends the generic spec sections with seven site sections (core job, data source & update plan, page map, SEO targets, monetization placement, maintenance plan, standing constraints); AdSense-default monetization; "How to use" note lives in the template header.
- [Where do generated websites live?](issues/08-site-repo-layout.md) — sites live at `sites/<slug>/` inside this workspace, each its own nested git repo with its own GitHub remote (deploy-friendly); the harness workspace itself becomes a git repo (documentation/state) with `sites/` gitignored so the repos stay independent; project stays at its current local path — no relocation; site repo creation happens at build time with user confirmation.

## Not yet specified

- Monetization playbook (AdSense vs affiliate vs other; when to apply; placement guidance in PRDs) — sharpens after first validated ideas show their monetization paths.
- Stages 5–8 workflow doc / checklists (build, SEO testing, preview, deploy) — waits until the first PRD exists.
- Skill refinement loop: what the first real scout/validate run teaches us to change.

## Out of scope

- Paid SEO tools/APIs (DataForSEO, Ahrefs, SEMrush, Keywords Everywhere).
- Automating anything on the human-checkpoint list (deployment, purchases, posting, AdSense).
- Scheduled/automatic discovery runs; V1 runs are manually triggered.
- Building harness machinery for stages 5–8 in V1.
- Multi-site scale/factory features (dashboards, portfolio analytics).
