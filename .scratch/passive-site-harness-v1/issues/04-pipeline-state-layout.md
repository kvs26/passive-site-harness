# Pipeline state layout and idea lifecycle

Type: grilling
Status: resolved

## Question

Decide the on-disk state convention: directory layout (e.g. `pipeline/ideas/<slug>/` with `evidence.md`, `scorecard.md`, `prd.md`), the idea lifecycle states (candidate → validated → picked → prd'd → built?; plus rejected/parked), where run logs live, and how a later session discovers current pipeline state. Output: the layout spec both skills will read/write.

## Answer

### Layout

```
pipeline/
├── board.md                          # derived global index — every idea + state; regenerated
│                                     # by any skill session that changes an idea's state
└── <niche-slug>/
    ├── niche.md                      # niche definition, date picked, market override,
    │                                 # Status: active | exhausted | parked
    ├── comparison-<YYYY-MM-DD>.md    # comparison brief across ≥3 validated ideas
    ├── runs/
    │   ├── <YYYY-MM-DD>-scout.md               # sources consulted, problem statements,
    │   │                                       # gate failures + reasons, candidates emitted
    │   └── <YYYY-MM-DD>-validate-<idea>.md     # what was dug, dead ends, inconclusive leads
    └── ideas/
        └── <idea-slug>/
            ├── idea.md               # Status: line (canonical), hook, problem statement,
            │                         # origin link to run file, dated history of state
            │                         # changes with reasons (incl. rejection reason)
            ├── dossier.md            # six-signal validation dossier, evidence embedded
            └── prd.md                # /to-spec output, once spec'd
```

### Lifecycle

`candidate → validated → picked → spec'd`, with side-exits `rejected` and `parked` at any point. `built` deliberately excluded from V1 (stages 5–8 out of scope); a later effort extends the vocabulary. Gate failures during scout never become ideas on disk — they live only in the run log.

### State recording & discovery

- The `Status:` line in `idea.md` is **canonical**; `pipeline/board.md` is a **derived view**, regenerated by whichever skill session changes state, always repairable from the `Status:` lines.
- A later session discovers state by opening `pipeline/board.md`; per-niche resumption starts at `niche.md`.
- Provenance is one hop: idea → origin run file; dossier signals embed their own evidence (per ticket 03).

Glossary terms (niche, dossier, board, lifecycle, run log) recorded in `CONTEXT.md`.
